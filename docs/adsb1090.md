# ADS-B 1090ES専用解析モード

最終更新: 2026-08-23

## 1. 位置づけ

ADS-B 1090ESは、汎用FSK/PSK VSAへ変調方式として追加せず、通信規格に特化した
専用解析モードとして実装する。汎用VSAは変調波形、シンボル同期、EVMなどを扱い、
専用モードは既知のフレーム構造、CRC、フィールド解釈、複数packet管理を所有する。

```text
IQRecording（共通）
  ├─ Generic VSA: FSK / PSK / 将来QAM
  └─ Standards
       ├─ ADS-B 1090ES（実装開始）
       └─ Bluetooth専用解析（将来）
```

Pluto取得、保存IQ、R&S iq-tar、振幅補正などは既存`IQRecording` contractを共有する。
規格固有decoderからPluto hardwareやファイル形式を直接参照しない。

## 2. 現時点の実装

実装場所は`pluto_sa/standards/adsb1090/`。

- 任意の4 MSPS以上のcomplex IQを入力
- IQ包絡線電力を生成
- Mode Sの8 us preambleを正規化相関で探索
- 4本の0.5 us pulseとquiet intervalによるshape/SNR検証
- 1 Mbps PPMを前半・後半0.5 usの積分電力比較で判定
- 56/112 bit messageに対応
- capture中の複数messageを時系列で列挙
- DF別のMode S 24-bit parity判定
  - DF17/18/19の通常CRC
  - DF0/4/5/16/20/21/24-31のAddress ParityとICAO候補復元
  - DF11のParity/Interrogator Identifier
  - Address ParityのICAO候補をCRC/PI検証済みの既知ICAOと照合してConfirmed化
- DF11/17/18の明示address、DF17/18のType Code
- DFに応じたCapability、Flight Status、Control Field、VS/CC/SLの表示
- Aircraft IdentificationのCallsign/Emitter Category
- Airborne PositionのQ-bit altitudeとraw CPR値
- Surface Positionのraw CPR値
- Airborne Velocityの東西・南北速度、対地速度、trackの基礎decode
- 専用Qt workspace
  - IQ Power
  - 選択packetのPPM soft decision（前半/後半0.5 us chip積分電力比、dB）
  - Packet List
  - Message Summary
- Generic VSAと共通のplot/Dock UI chrome
  - 左ドラッグ: Rect Zoom
  - 中ドラッグ: Pan
  - 右クリック: Reset、trace基準View All、既存pyqtgraph menu
  - Dock titleのbold/130 % fontを共通helperで管理
- Packet Listへmeasurement開始からの経過時間、OS local time、raw messageを記録
- Packet Listへdata ON chipの平均電力をdBmで記録
- `File > Export Packet List...`またはPacket List右クリックから、全履歴をschema/version付き
  UTF-8 JSON Lines（`.jsonl`）としてexportする。各行へ時刻、raw message、DF、ICAO、
  parity、電力、SNR、decode fieldを自己完結形式で保持する。
- IQ Powerの表示下限を-140 dBmで足切り（検出・電力演算の元データは変更しない）
- Pluto Run ContinuousでIQ streamを連続取得し、検出packetを履歴へ追記
  - UIのCapture値と独立した内部50 ms chunkで読み、最初だけRX bufferをfresh開始する
  - 2 chunk目以降はbufferを破棄せず、160 us overlap解析でchunk境界packetを検出する
  - UIのCapture値はIQ Power横軸の履歴時間を定義する
  - packet未検出chunkではplot/tableを更新しない
- Pluto Run Singleはpacketを検出するまで連続待受けし、検出後にCapture設定時間だけ
  受信を継続してから結果を確定する。同じRun Single操作で待受けを中止できる。
- 同一トップレベルウィンドウの`Analysis Mode`から汎用VSAとADS-B workspaceを切替
- 汎用VSAからADS-Bへ切り替えた場合は現在のIQを引渡し可能
- 専用workspaceから1090 MHz Pluto Run Singleが可能
  - 既定8 MSPS
  - 既定RF BW 4 MHz
  - 既定capture 250 ms
  - 既定internal gain 50 dB
- toolbarの`Preamble SNR Threshold`でpreamble pulse/quiet積分電力比の検出閾値を
  -20～40 dB、0.5 dB刻みで設定可能。実空間の約5 dB packetを取りこぼさないよう既定値は
  5.0 dB。ファイル解析、Single、Continuousの
  すべてへ適用し、Continuous中の変更は次の内部解析blockから反映する。

ADS-Bのユーザー設定は汎用VSAのMeas Configと共有しない。専用の
`PlutoSA/PlutoVSA-ADSB1090`設定ストアに次を自動保存し、次回起動時に復元する。

- Sample Rate
- Capture表示時間
- ADS-B専用Internal Gain
- Preamble SNR Threshold
- IQファイル読込フォルダ
- Packet List出力フォルダ

Continuous/SingleのPluto受信では、USB/IIO取得とADS-B DSPを別スレッドに分離する。
取得スレッドは50 ms IQブロックを継続取得し、DSPワーカーがpreamble相関、PPM復調、
CRC/parity判定、表示用リングバッファ処理を順次実行する。GUIスレッドは完成したpacketを
Packet Listへ追加し、選択・スクロール等の操作を受け付ける。IQ Power表示だけはGUI負荷を
抑えるため最大100,000点のmin/max peak envelopeへ間引くが、検出・復調用IQは間引かない。
Packet Listは最新行を表示中なら新着packetへ追従し、過去行をユーザーが選択した場合は
連続受信中もその選択を維持する。

ADS-B workspaceは汎用VSAと同じ2行×3列の等分Dock layoutを使用する。

| | 左 | 中 | 右 |
|---|---|---|---|
| 上 | IQ Power | Packet List | Detected Aircraft |
| 下 | PPM Demodulation | Message Summary | Aircraft Summary |

Detected AircraftはCRC/parityで確認できたICAOごとにpacketを集約する。Aircraft Summaryには
Callsign、Emitter Category、初回/最終検出時刻、packet数、確認済みparity数、DF/TC履歴、
最新高度・対地速度・track、最新/平均/peak ON power、preamble SNR、相関、raw CPR、
最新raw messageを表示する。緯度経度はCPR pairからの位置復元が未実装のためraw値とする。

Standalone起動:

```powershell
python -m pluto_sa.standards.adsb1090.main
```

通常の`python -m pluto_sa.vsa.main`では`PlutoAnalysisWindow`が1つの
`PlutoLiveSource`を所有し、Generic VSAとADS-B workspaceへ共有する。両workspaceを
同時にtop-level windowとして表示しない。Pluto captureまたはGeneric DSP解析の実行中は
mode切替を拒否し、hardware reconfigure、RX buffer、close処理の競合を防ぐ。各workspaceは
独自menu、dock layout、result modelを保持するが、切替後も設定と直前の結果を保持する。

## 3. 検証状態

公開例として広く使われる既知DF17 frameをpytestへ固定した。

- `8D40621D58C382D690C8AC2863A7`
  - CRC valid
  - ICAO `40621D`
  - Type Code 11
  - altitude 38,000 ft
- `8D4840D6202CC371C32CE0576098`
  - CRC valid
  - ICAO `4840D6`
  - callsign `KLM1023`

8 MSPSのsynthetic PPM IQでは、1 capture中の複数frame検出、CRC異常frameの保持／除外、
field decodeを検証済み。DF5の実測例`28201507C8E5CD`はAddress Parity syndrome
`84D28E`をICAO候補として復元する回帰試験へ追加した。実空間1090 MHz captureの検出閾値、隣接Mode A/C応答、重畳packet、
Pluto gainは未検証。

既定Preamble SNR 5 dBと相関0.72は受信機実装上の経験的閾値であり、ICAOが定める
一律の復号閾値ではない。ここでのSNRは8 us preamble内のpulse/quiet積分電力比である。

手動確認用IQとして`tests/fixtures/adsb1090_multi_8msps.npz`を管理する。1090 MHz、
8 MSPS、2 msの中にCallsign、even/odd Airborne Position、Velocityの4つのCRC valid
DF17を収録し、振幅差、27.5 kHz CFO、AWGN、DC offset、有限edgeを与えている。同名の
`.npz.json`が期待decode結果である。再生成は次で行う。

```powershell
python tools/generate_adsb1090_iq.py
```

2026-08-22に接続中のPlutoで1090 MHz、要求8 MSPS、RF BW 4 MHz、20 ms、internal
gain 50 dBのFree Run取得を実施した。実Fs 7,999,999 S/s、160,000 complex sampleを取得し、
専用解析器まで例外なく完走した。この20 ms区間の検出messageは0件であり、antenna条件と
観測時間が不明なためRF受信性能・検出感度の合格判定には使用しない。

10. 978 UATは別規格モジュールとして扱う

現時点のCRC strict設定はcoreに存在するが、UIではCRC異常messageも観測・debugのため表示する。
Airborne位置は、同一ICAOかつ10秒以内のeven/odd CPR pairが揃った場合にglobal decodeして
緯度経度を表示する。片側だけのCPR、10秒を超えたpair、latitude zone不整合のpairは
位置として採用しない。Surface CPRの位置復元は基準位置が必要なため現時点では未対応。

Aircraft stateには、取得できた範囲でAir/Ground、緯度・経度、高度（ft / m）、
対地速度（kt / km/h）、垂直速度（ft/min / m/s）とそのbarometric/GNSS sourceを保持する。

外部機体databaseはdecoder/DSPから分離し、ICAOをキーに問い合わせるprovider境界と
local cacheを介して実装した。登録記号、型式、maker、operator、countryなどは外部data由来と
取得時刻を明示し、network障害やrate limitで受信・復調・GUIを停止させない。

### 外部機体databaseと位置履歴（2026-08-23）

OpenSky Aircraft Metadata CSVをlocal SQLiteへ取り込む実装を追加した。`File > Aircraft
Database`から、保存済みCSVのimportまたはOpenSky公式snapshotのdownload/updateを実行する。
CSV parse、download、SQLite index再構築は専用threadで行い、完成したdatabaseへatomicに
差し替える。scan中のIQ capture・ADS-B decode・GUI操作をdatabase更新で停止させない。

ICAO lookup結果として、登録記号、manufacturer、model、type code、serial number、operator、
operator callsign、owner、countryをAircraft Detailsへ表示する。外部値は`(DB)`表記で、電文から
decodeしたcallsign・position・altitude等と区別する。OpenSky側がsnapshotの陳腐化と無保証を
明記しているため、自動でonline位置を上書きせず、取得したADS-B電文を測定値のsource of truthとする。

Aircraft Detailsは`Details`と`Position History`のtab切り替え式とした。位置履歴は同一ICAOの
validなglobal airborne CPR結果を最大10,000点保持する。`Position History`を初めて開いた時点で
`QWebEngineView`をlazy生成し、Leaflet 1.9.4とOpenStreetMap standard tile上へ軌跡と最新位置を
表示する。軌跡は道路色と重なりにくいmagentaをdark casing付きで描画する。現在位置にはcyanの
aircraft iconを表示し、velocity電文のtrack angleへ回転する。track angleが未取得の場合は直近2位置の
bearingを代用し、いずれも得られない場合のみnorth向きとする。OpenStreetMap attributionは地図上に
常時表示する。地図を開かないscanではWebEngineを
起動せず、tile/network処理をIQ capture・decode・aircraft state更新から分離する。表示へ渡す履歴は
最新5,000点を上限とする。6個のdockはmain window resize時に3列を再均等化し、横方向の合計が
client areaへ収まる。standard tileとLeaflet assetの取得にはinternet接続が必要である。またWindows
環境でのQt WebEngine終了時例外を避けるため、この地図ではWebGL/accelerated 2D canvasを無効化し、
ADS-B windowの終了処理でWebEngineのloadとcallbackをdock破棄より先に停止する。

### Display responsiveness（2026-08-23）

IQ Powerの表示下限は`-120 dBm`とする。continuous scan中のGUI更新は100 ms単位でまとめ、検出packetは
全件Packet Listへ保持しながら、Power trace・選択詳細の再描画はbatch内の最新結果へ集約する。
Power traceはpeak envelopeを維持した最大25,000点へ表示用decimationする。また`Position History`が
非表示の間はLeafletへのtrack転送を保留する。これらは受信およびdecode処理には影響しない表示負荷対策である。

### ADSBDB route enrichment（2026-08-23）

Callsignを受信した機体について、ADSBDBのcallsign APIからorigin、destination、airlineを取得する。
network照会はIQ受信・decode・GUI threadから分離したbackground workerで行い、同一session中はcallsign単位で
成功結果と「該当なし」の双方をcacheする。Origin/DestinationはDetected Aircraftへ、詳細な空港名とairlineは
Aircraft Detailsへ表示する。

この情報はADS-B messageそのものではなく外部データによるbest-effortの補足情報である。該当便なし、HTTP error、
timeout、応答形式不正を含む取得失敗は測定errorにせず、表示を`-`としてcapture・decode・packet list更新を継続する。
古い運航情報を永続化しないためroute cacheはapplication終了時に破棄する。

### Receiver locationとLocal CPR（2026-08-23）

`Analysis Mode > Receiver Location...`またはcapture toolbarのreceiver buttonから、受信機の
latitude/longitudeをdecimal degreesで設定する。設定dialogでは直接入力に加え`Select on Map...`を
選択でき、その場合は`Position History`をreceiver selection modeへ切り替え、Leaflet地図上のclick
位置を確認後に保存する。`RX` markerは選択中の仮位置確認にだけ表示し、確定後は地図から消す。
確定座標はADS-B専用`QSettings`へ保存して次回起動時に復元する。receiver locationは汎用VSAの
Configと共有しない。

Airborne positionは、10秒以内のvalidなEven/Odd pairがあれば従来どおりGlobal CPRを最優先する。
pairが揃わない単独frameでは、直前のvalidなaircraft position、次にreceiver locationをreferenceとする
Local CPRを試行する。referenceとcandidateの距離が180 NMを超える結果は採用せず、直前位置がある場合は
1,500 ktと2 NMのmarginによるteleport rejectionも適用する。Aircraft Detailsには`Position Source`、
`Position Reference`、`Distance from Receiver`を表示し、Global/Local CPRの由来を追跡可能にする。
